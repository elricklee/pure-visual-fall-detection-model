# 组员乙 Day 2 基线模型性能评测报告

评测日期：2026-07-24  
评测对象：`artifacts/onnx/yolov8n_pose_384_fp32.onnx`

## 1. 结论

当前 YOLOv8n-pose 基线模型已经满足赛题中可在 PC 端直接验证的两项硬性规模要求：

- 参数量 3.29M，低于 20M；
- FP32 初始化权重 13.1599MB，低于 80MB。

模型使用固定输入、标准 ONNX 算子，NMS、关键点解码和时序判断位于模型外，具备进一步转换到常见端侧 NPU 的结构基础。

当前合规状态为 `design_ready_unverified`：6 项通过、2 项为设计目标、0 项失败、0 项缺失。端侧 100ms 和 NPU 运行内存 20MB 尚无真实设备证据，不能写成实测通过。

## 4. PC端参考性能

测试环境：

- Windows 11；
- ONNX Runtime 1.27.0；
- `CPUExecutionProvider`；
- 输入为真实样例预处理后的 FP32 张量；
- 预热 20 次，正式运行 100 次。

| 指标 | PC参考值 |
|---|---:|
| 最小延迟 | 16.8539ms |
| 平均延迟 | 269.1716ms |
| 中位数 | 224.3909ms |
| P90 | 579.9470ms |
| P95 | 589.4118ms |
| P99 | 674.9375ms |
| 最大延迟 | 727.2645ms |
| 标准差 | 248.1754ms |
| 按平均值换算FPS | 3.715 |
| 观测峰值进程RSS | 102.3304MB |

该数据只包含 ONNX 模型推理，不含视频解码、letterbox、NMS、关键点解码、时序判断和报警输出。

平均值与 P95 差距较大，表明当前 Windows CPU 测试存在明显抖动。可能影响因素包括系统负载、通用 CPU Provider 调度和线程配置。它可以作为回归基线，但不能替代具体 NPU 的性能结论。

## 6. 算子与NPU可行性

模型主要算子包括：

```text
Conv, Add, Mul, Concat, MaxPool, Resize, Reshape, Sigmoid,
Softmax, Split, Slice, Gather, Transpose, Shape, Div, Sub
```

当前没有发现需要立即判定为高风险的自定义算子、动态控制流或动态 Shape。最终兼容性仍需在确定芯片后，通过厂商转换日志验证。

部署建议保持：

- Batch 固定为 1；
- 输入固定为 384；
- NMS、关键点解码和时序状态机放在 NPU 模型外；
- 优先验证 FP16，再进行 INT8 校准；
- 不在未测试前宣称适配全部海思或瑞芯微型号。

## 7. 主要风险

| 优先级 | 风险 | 影响 |
|---|---|---|
| P0 | 当前没有独立测试集 | 无法形成可信的最终精度、误报和漏报结论 |
| P0 | 标签含自动生成或伪关键点 | Pose指标可能偏高或不稳定 |
| P0 | NPU延迟和运行内存未实测 | 100ms、20MB只能写成设计目标 |
| P1 | PC CPU延迟抖动较大 | 不适合作为对外宣传的端侧性能数字 |
| P1 | 尚无完整端到端耗时拆分 | 无法定位预处理、NMS和时序逻辑占比 |
| P1 | 红外、微光、遮挡证据不足 | 无法证明复杂场景泛化 |
| P2 | 多人时序状态未按track_id隔离 | 多人场景可能发生状态串扰 |

## 8. 给甲的优化建议

1. 继续以 384 固定输入作为端侧主基线，不建议直接使用 640 作为低算力部署版本。
2. 在验证精度前不要盲目缩小到 320；如果后续端侧不满足 100ms，再将 320 作为速度兜底版本。
3. 准备 300–500 张代表性校准图片，覆盖正常动作、跌倒、遮挡、微光和红外，用于 INT8 校准。
4. 量化后必须复测关键点指标和视频级误报/漏报，建议内部控制 Pose mAP50-95 下降不超过 2 个百分点。
5. 继续保持固定 Shape、标准算子和模型外 NMS；不要引入自定义算子或动态控制流。
6. 建立按 `track_id` 独立维护的时序状态，或者在 MVP 文档中明确单人场景边界。
7. 补充独立测试集和场景标签，避免使用训练/验证素材得出最终准确率。
8. Day 4 联调时分开记录预处理、模型、NMS/解码、时序判断及完整端到端耗时。
